# Профили сайтов: реализация и проверка

Дата обновления: 2026-09-23.

## Источники и границы проверки

- GitHub: DOM-признаки из [ранее выполненной проверки](github-dom-notes.md); текущая регрессия проверяется локальными тестами, повторная проверка живого сайта не выполнялась.
- GitLab: поля `name="note[note]"`, `.js-note-text` и `data-testid="reply-field"` описаны в [исходном компоненте GitLab](https://gitlab.com/gitlab-org/gitlab/-/raw/master/app/assets/javascripts/notes/components/note_form.vue). Профиль предназначен для textarea в Markdown-режиме. Обёртка и фактическое поведение сайта требуют ручной проверки.
- Bitbucket: [документация Atlassian](https://support.atlassian.com/bitbucket-cloud/docs/review-code-in-a-pull-request/) описывает визуальный редактор. Селекторы `.ProseMirror[contenteditable="true"]` и `.ak-editor-content-area, .akEditor, form` — предварительные предположения, не подтверждённый DOM Bitbucket. При несовпадении используйте диагностику и измените профиль.
- `test/fixtures/editors.html` — синтетические примеры, не снимки сайтов. Корпоративный пример моделирует два независимых комментария; корпоративная версия GitLab/Bitbucket не проверена.
- По решению пользователя реальные проверки GitLab/Bitbucket выполняет пользователь. Успех локальных тестов не подтверждает отправку текста этими сайтами.

## Страница настроек

Профили редактируются в отдельной вкладке: gear «Настройки» справа от темы в popup или «Сведения» → «Параметры расширения» в chrome://extensions. Форма видна сразу; закрытие popup не закрывает вкладку. Диагностика открывает эту страницу с выбранным профилем. Общая тема обновляется без потери черновика.

## Разрешения Chrome

Используются [permissions.request / contains](https://developer.chrome.com/docs/extensions/reference/api/permissions) и [scripting.registerContentScripts](https://developer.chrome.com/docs/extensions/reference/api/scripting). Запрос доступа вызывается непосредственно нажатием кнопки пользователя. Динамическая регистрация доступна с Chrome 96; минимальная версия расширения — Chrome 102 с используемыми Promise API.

GitHub имеет постоянный доступ. Скрипт запускается на GitHub origin для поддержки SPA-переходов, но панель ограничена маской PR. Другие сайты требуют отдельного разрешения. Chrome разрешает доступ к хосту на всех портах; внутри расширения профиль дополнительно проверяет точный origin, включая порт. Изменение адреса и восстановление профиля не отзывают разрешения Chrome автоматически. Все три профиля включены постоянно. Доступ можно отозвать в настройках расширения Chrome.

Service worker синхронизирует регистрации при запуске, установке, изменении профилей и разрешений. Снятие регистрации само по себе не удаляет уже внедрённый UI: активным вкладкам отдельно отправляется команда очистки. Не доступные для связи документы очищаются после перезагрузки.

## Вставка текста

Textarea использует нативный setter и всплывающий `input`, чтобы управляемый редактор получил изменение. Для визуального редактора используется экспериментальная браузерная команда `insertText` в начале выделения: расширение не заменяет HTML целиком. Совместимость этой команды с конкретным редактором, его историей undo и отправкой требует проверки. Если операция отклонена, появляется сообщение; принудительная подмена HTML не выполняется.

Селекторы работают в основном документе. Закрытый Shadow DOM и редакторы внутри iframe не поддерживаются. Пользовательский JavaScript не выполняется.

## Локальные проверки

`npm test` проверяет:

- выбор профиля, точный адрес, маски и фиксированный порядок при пересечении, совместимость старых данных, сохранение и сброс;
- расположение панели, несколько комментариев, динамическое появление и удаление полей, поздний anchor, SPA-переходы;
- содержимое textarea, курсор, фокус и `input`, отсутствие повторного префикса;
- уведомления, их закрытие, подавление повторов и восстановление;
- автосохранение полей страницы настроек, ошибки ввода и записи, быстрый ввод, задержанные ответы, смену профиля и сброс во время записи;
- жизненный цикл worker с mock Chrome API: разрешения, отзыв, повторная регистрация и подключение, очистку старых регистраций и ошибки;
- регрессию настроек labels и темы.

DOM-стенд не рассчитывает геометрию, а API mocks не запускают настоящий Chrome. Визуальная проверка и проверка реального жизненного цикла MV3 остаются отдельными пунктами приёмки.

## Ручная приёмка GitLab и Bitbucket

1. Перезагрузите unpacked extension. Нажмите gear «Настройки» справа от переключателя темы в popup, выберите профиль и разрешите доступ к сайту.
2. Откройте MR/PR и поле комментария к строке. Для GitLab используйте Markdown-режим.
3. Если панель не появилась, проверьте доступ, адрес, маски и CSS-селектор редактора. Автоматическое уведомление о месте панели позволяет перейти к настройкам профиля. Внутренние контейнеры и тип редактора определяются предустановкой.
4. Введите черновик, нажмите label. Проверьте сохранение текста и форматирования, положение курсора и реакцию кнопки отправки. Проверьте повторный клик и undo для визуального редактора.
5. Самостоятельно проверьте отправку тестового комментария в подходящем репозитории и отмену черновика.
6. Выберите положение снизу, дождитесь «Сохранено» и проверьте два открытых комментария.
7. Проверьте быстрый ввод, смену профиля, закрытие и повторное открытие страницы настроек. Некорректное поле должно показывать ошибку без замены рабочей конфигурации. Кнопка «Восстановить профиль» возвращает предустановку, включая CSS, даже во время записи.
8. Для корпоративного сайта измените адрес, пути и селектор соответствующего встроенного профиля. Адаптер менять нельзя: Bitbucket Data Center с textarea вместо визуального редактора Cloud этой предустановкой не поддерживается.

## Совместимость хранилища

Эффективная конфигурация содержит только GitHub, GitLab и Bitbucket в этом порядке. Схема остаётся `schemaVersion: 1`. Старые `custom` сохраняются без применения; чтение не записывает миграцию. Для встроенных профилей принимаются только допустимые `origin`, `paths`, `editorSelector` и `placement` (`before`/`after`), а также строковое `panelCss`. Другие поля берутся из defaults. Устаревшее положение или неверное отдельное поле получает значение по умолчанию. Сохранение и сброс неизвестного id запрещены; неизвестная версия схемы не перезаписывается.

Страница настроек отправляет каждый корректный снимок сразу в последовательную очередь worker, без debounce. Ответы не перерисовывают поля; черновики и статусы учитываются отдельно по профилю и версии. Кнопка доступа работает только для подтверждённого снимка. После ошибки записи повтор возможен изменением поля. Сброс упорядочен после предыдущих записей, новые изменения идут после сброса.

Откат версии сохраняет доступ к прежним custom-данным, но изменённые или восстановленные overrides автоматически не возвращаются. Labels и тема не затрагиваются.


## CSS панели

В блоке «Стили панели» отображается полный текст CSS из `src/panel-styles.js` либо сохранённый текст выбранного профиля. Поле использует моноширинный шрифт, имеет доступное название «CSS панели и кнопок» и отключённую проверку орфографии. Статус CSS независим от статуса остальных полей.

Необязательное `overrides[id].panelCss` не меняет схему 1. Отсутствие и неверный тип означают актуальный стандарт; пустая строка означает отсутствие собственных правил. Исходные пробелы, комментарии и незавершённый CSS сохраняются. Парсер браузера может игнорировать ошибочные или неподдерживаемые правила; расширение не валидирует CSS и не ограничивает произвольные селекторы автоматически. CSP и загрузка внешних ресурсов подчиняются браузеру, новых разрешений нет.

Worker сериализует частичные операции CSS и объединяет их с последним состоянием. Обычное сохранение адреса/масок/селектора/положения не перезаписывает CSS устаревшим снимком. Черновики и версии ответов CSS учитываются отдельно для каждого профиля. «Восстановить» удаляет только `panelCss`, работает при невалидном адресе и сохраняет другие черновики. «Восстановить профиль» удаляет все overrides выбранного профиля; обе группы операций согласованы с ожидающими записями и более поздними правками.

В документе работает один собственный `style[data-cc-panel-style]`: пользовательский CSS заменяет стандартный целиком. Удаление правила в редакторе действительно удаляет его действие; пустой CSS не включает скрытые стандарты. Обновление текста style не пересоздаёт панели и не меняет комментарии. При выходе за маску, смене профиля или отзыве доступа старый стиль удаляется в доступных контекстах. Диагностика остаётся в `src/content-style.css`. При обновлении unpacked extension перезагрузите расширение и уже открытые вкладки, чтобы заменить старые контексты и статический CSS.

Стандартный ресурс сохраняет локальные правки оформления, существовавшие перед этим change: закомментированные отступы/фон/границы панели и media-блок тёмной темы. Кнопки продолжают использовать CSS-переменные сайта.

## Приёмка CSS в Chrome — 2026-09-23

Проверка выполнена в Chrome 153.0.8010.53 через Playwright с установленным unpacked extension, настоящими options, service worker и storage. Ответ страницы по тестовому GitHub PR URL подменён локальным HTML с двумя формами и третьим редактором без контейнера для диагностики; это не проверка живого DOM GitHub.

Проверены:

- фактический стандартный текст в редакторе, изменение цвета кнопок, gap 19px и padding 17px сразу на двух панелях;
- удаление правила панели: display стал block, padding — 0px; скрытого стандартного слоя нет;
- пустой CSS после повторного открытия options;
- отдельный сброс при невалидном адресе с сохранением черновика, полный сброс во время записи;
- светлая и тёмная тема options; кнопки панели с CSS-переменными светлой/тёмной темы сайта;
- неизменность оформления диагностики при CSS классов панели; после исправления и перезагрузки расширения три последовательные записи CSS оставляют ровно одно уведомление;
- удаление и восстановление стиля при SPA-переходах, сохранность черновиков, единственный style-элемент и отсутствие повторных мутаций style в установившемся состоянии.

Локальные node-тесты дополнительно проверяют ошибки записи, задержанные и переставленные ответы, независимость профилей, частичные записи worker и отзыв доступа. Реальные GitLab/Bitbucket, корпоративные установки, отправка комментариев и поведение CSP внешних ресурсов в этой приёмке не проверялись; ручная проверка остаётся за пользователем по принятой практике проекта.
