# extension-packaging Specification

## Purpose

Описывает packaging-поведение Chrome extension, которое влияет на установку и отображение расширения в Chrome UI, но не относится напрямую к popup или GitHub Pull Request comment UI.

## Requirements

### Requirement: Расширение имеет собственную иконку в Chrome UI

Расширение SHALL объявлять собственную иконку для Chrome extension UI, включая toolbar/action icon и manifest icons.

#### Scenario: Пользователь видит расширение в панели Chrome

- **WHEN** пользователь устанавливает расширение как unpacked extension
- **THEN** Chrome показывает для расширения собственную иконку вместо дефолтной иконки расширения

#### Scenario: Chrome запрашивает стандартные размеры иконки

- **WHEN** Chrome отображает расширение в местах, где нужны размеры `16`, `32`, `48` или `128`
- **THEN** manifest ссылается на существующие icon assets этих размеров

### Requirement: Отдельный локальный пакет Safari

Проект SHALL предоставлять воспроизводимый Safari-пакет из общих исходников расширения, содержащий manifest и все необходимые локальные ресурсы. Создание Safari-пакета SHALL NOT изменять исходный Chrome manifest, ресурсы или сохранённые данные установленного Chrome-расширения.

#### Scenario: Подготовка пакета
- **WHEN** разработчик выполняет документированную команду подготовки Safari-пакета
- **THEN** создаётся отдельная папка, которую Safari принимает как Web Extension, с popup, options, иконками, content scripts, фоновым контекстом, шрифтом и emoji-ресурсами

#### Scenario: Повторная подготовка
- **WHEN** разработчик меняет общие исходники и повторяет команду
- **THEN** пакет отражает текущие исходники без устаревших ресурсов, а Chrome продолжает загружаться прежним способом

### Requirement: Документированный локальный запуск Safari на macOS

Документация SHALL описывать проверенные версии macOS/Safari, подготовку, временную установку через Developer settings, включение, разрешение сайтов, перезагрузку после изменений и удаление. Она SHALL явно сообщать, что Safari удаляет временное расширение при выходе или через 24 часа и что восстановление данных после повторной установки не гарантируется. Способ SHALL NOT требовать App Store, платного developer account или Xcode. Поддержка старых версий Safari без временной загрузки папки SHALL NOT заявляться.

#### Scenario: Первый запуск
- **WHEN** пользователь выполняет инструкцию на проверенной версии Safari для macOS
- **THEN** он может загрузить пакет, включить расширение, предоставить доступ сайту и открыть popup и панель комментариев

#### Scenario: Завершение временной установки
- **WHEN** пользователь выходит из Safari либо истекает срок временной установки
- **THEN** документация объясняет необходимость повторного добавления и предоставления доступа и не обещает постоянную установку или сохранность данных после удаления

### Requirement: Отдельный локальный пакет Firefox
Проект SHALL предоставлять `npm run package:firefox`, создающую в `dist/firefox` отдельный MV3-пакет из общих исходников для временной установки Firefox desktop. Пакет SHALL включать совместимый manifest, стабильный add-on ID и все локальные ресурсы интерфейса и фонового контекста. Упаковка SHALL NOT менять исходники, Chrome manifest, Safari output или данные установленных расширений.

#### Scenario: Подготовка и загрузка
- **WHEN** разработчик выполняет команду упаковки и выбирает manifest пакета в Firefox
- **THEN** Firefox загружает расширение, запускает фоновый контекст, открывает popup и Settings без ошибок отсутствующих ресурсов

#### Scenario: Повторная упаковка
- **WHEN** разработчик обновляет исходники и повторяет команду
- **THEN** пакет отражает текущие ресурсы без устаревших файлов, сохраняет add-on ID и не изменяет соседние пакеты; одинаковые входные файлы дают одинаковое содержимое

### Requirement: Документированная временная установка Firefox
Документация SHALL описывать сборку, установку через `about:debugging`, доступ к сайтам, Reload после обновления, удаление и фактически проверенные версии Firefox/ОС. Она SHALL явно сообщать, что установка временная и удаляется при перезапуске Firefox, а восстановление данных после удаления не гарантируется. Подпись и публикация SHALL NOT требоваться для этого способа.

#### Scenario: Первый локальный запуск
- **WHEN** пользователь выполняет инструкцию на проверенной версии Firefox desktop
- **THEN** он может выбрать `dist/firefox/manifest.json`, открыть popup, разрешить GitHub и использовать панель в PR

#### Scenario: Перезапуск браузера
- **WHEN** пользователь перезапускает Firefox после временной установки
- **THEN** инструкция объясняет необходимость повторной загрузки и проверки доступа без обещания постоянной установки или сохранности удалённых данных

### Requirement: Единые команды разработки Firefox
Проект SHALL предоставлять make build-firefox, lint-firefox, run-firefox и package-firefox после документированной установки инструментов. Каждая команда SHALL использовать актуальный Firefox-пакет; сбой подготовки или обязательной проверки SHALL завершать операцию с ненулевым кодом. Отсутствующий инструмент SHALL сопровождаться понятной диагностикой без скрытой установки.

#### Scenario: Подготовка папки
- **WHEN** разработчик выполняет make build-firefox
- **THEN** dist/firefox содержит актуальный пакет, эквивалентный результату существующей npm run package:firefox

#### Scenario: Проверка пакета
- **WHEN** разработчик выполняет make lint-firefox
- **THEN** проверяется Firefox manifest и его ресурсы, диагностика видна в терминале, а ошибки дают ненулевой код возврата

#### Scenario: Неуспешная проверка
- **WHEN** обязательная проверка перед запуском или ZIP-упаковкой обнаруживает ошибку
- **THEN** браузер не запускается, новый ZIP не создаётся и команда не сообщает об успешном результате

### Requirement: Временный запуск Firefox из команды
make run-firefox SHALL подготавливать и проверять пакет, затем запускать Firefox с временным расширением в отдельном профиле по умолчанию. Команда SHALL позволять указать путь Firefox через FIREFOX_BIN, включая путь с пробелами. Документация SHALL объяснять повторный запуск после изменений исходников и ограничения временной установки.

#### Scenario: Запуск для разработки
- **WHEN** разработчик выполняет make run-firefox при установленном Firefox и инструментах
- **THEN** браузер запускается с текущим расширением без ручного выбора manifest и без изменения существующего пользовательского профиля

#### Scenario: Явный путь браузера
- **WHEN** разработчик задаёт FIREFOX_BIN с корректным путём к Firefox
- **THEN** запускается указанный браузер; неверный путь завершается понятной ошибкой

### Requirement: Версионный Firefox ZIP
make package-firefox SHALL создавать dist/conventional-comments-firefox-<version>.zip, где version соответствует manifest расширения, после успешной проверки. Архив SHALL содержать Firefox manifest в корне, необходимые ресурсы и лицензии, без инструментов разработки и соседних браузерных пакетов. Это SHALL быть неподписанный пакет без обещания постоянной установки.

#### Scenario: Создание архива
- **WHEN** разработчик выполняет make package-firefox
- **THEN** создаётся отдельный Firefox ZIP, путь печатается в терминале, а Chrome ZIP и Safari-пакет остаются неизменными

#### Scenario: Повторная сборка
- **WHEN** исходный ресурс изменён или удалён и команда выполнена повторно для той же версии
- **THEN** архив содержит актуальные ресурсы без устаревших файлов и без вложенного предыдущего архива

### Requirement: Актуальная справка сборки
make help и документация SHALL описывать Firefox-команды, установку инструментов, выходные файлы и назначение прежней make package как Chrome ZIP. Существующие команды подготовки Firefox-папки и Safari-пакета SHALL сохранять своё поведение.

#### Scenario: Выбор команды
- **WHEN** разработчик читает make help и инструкцию Firefox
- **THEN** он может отличить подготовку папки, проверку, временный запуск и создание неподписанного ZIP и найти необходимые команды установки зависимостей
