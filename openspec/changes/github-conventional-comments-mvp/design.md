## Context

См. `proposal.md` для мотивации и границ MVP. Репозиторий находится в начале проекта, поэтому дизайн должен оставаться простым: одно Chrome-расширение для GitHub Pull Requests без серверной части, настроек и поддержки других code review платформ.

GitHub динамически открывает и закрывает формы комментариев к строкам кода, поэтому расширению нужно реагировать на изменения DOM после загрузки страницы.

## Goals / Non-Goals

**Goals:**

- Встроиться в стандартное поле комментария GitHub без замены GitHub UI.
- Добавлять панель labels только рядом с открытым полем комментария.
- Использовать минимальные разрешения Chrome Extension.
- Сохранить простую структуру проекта, подходящую для первого MVP.

**Non-Goals:**

- Поддержка GitLab и Bitbucket.
- Popup, options page и пользовательские настройки.
- Генерация комментариев, AI-подсказки или анализ кода.
- Синхронизация данных или хранение пользовательского состояния.
- Автоматическая публикация в Chrome Web Store.

## Decisions

### Manifest V3 и статический content script

Расширение будет использовать Chrome Extension Manifest V3 со статически объявленным content script для страниц GitHub.

Рationale: MVP должен запускаться автоматически на известных страницах и не требует background service worker, popup или программной инъекции. Это уменьшает количество кода и разрешений.

Alternatives considered:

- Programmatic injection через background service worker: избыточно для MVP, потому что пользователь не должен нажимать кнопку расширения.
- Userscript без Chrome Extension: быстрее для прототипа, но не соответствует цели проекта.

### Ограничить match patterns GitHub

Content script должен запускаться только на GitHub, предпочтительно на URL Pull Request. Если Chrome match pattern окажется недостаточно точным для всех PR вкладок, дополнительная фильтрация выполняется внутри content script по `location`.

Рationale: расширение не должно получать доступ к лишним сайтам.

Alternatives considered:

- Широкий доступ ко всем сайтам: проще технически, но хуже для доверия и безопасности.
- Поддержка нескольких хостов сразу: противоречит решению оставить GitLab и Bitbucket на потом.

### Наблюдать за появлением форм через MutationObserver

Content script будет использовать `MutationObserver`, чтобы находить поля комментариев, которые GitHub добавляет после клика пользователя.

Рationale: формы review comments появляются динамически, поэтому обработка только при загрузке страницы будет ненадежной.

Alternatives considered:

- Обработчики клика по кнопкам GitHub: сильнее завязаны на внутреннюю разметку GitHub.
- Периодический polling: проще, но хуже по производительности и менее аккуратен.

### Вставлять только label prefix

Клик по label вставляет строку вида `suggestion: ` в начало поля комментария. Decorations вроде `(non-blocking)` не добавляются в MVP.

Рationale: это самая короткая полезная фича, которая учит пользователя формату Conventional Comments и не усложняет UI.

Alternatives considered:

- Вставлять полный шаблон с subject/discussion: может мешать пользователю и требует больше редактирования.
- Добавить decorations сразу: полезно, но расширяет scope первой версии.

### Не хранить пользовательские данные

MVP не использует storage и не сохраняет введенный текст, выбранные labels или историю комментариев.

Рationale: расширению не нужно состояние для первой фичи, а отсутствие хранения снижает риски приватности.

Alternatives considered:

- Сохранять часто используемые labels: это настройка, которую лучше добавить отдельным изменением.

## Risks / Trade-offs

- GitHub может изменить DOM review forms -> использовать несколько устойчивых признаков поля комментария и держать код интеграции изолированным.
- GitHub может использовать разные редакторы на разных страницах Pull Request -> проверить поведение на Files changed и review flow перед реализацией.
- Панель может визуально конфликтовать с GitHub UI -> стилизовать ее с минимальным CSS и не перекрывать стандартные элементы.
- Несколько открытых полей комментариев могут появиться одновременно -> помечать уже обработанные поля, чтобы не добавлять панель повторно.

## Migration Plan

Так как проект начинается с нуля, миграции нет. Для локальной проверки расширение загружается в Chrome как unpacked extension. Откат первой версии заключается в отключении или удалении расширения из Chrome.

## Open Questions

- Какие точные DOM-селекторы GitHub окажутся самыми устойчивыми для поля комментария к строке кода; это нужно уточнить во время реализации на реальной странице Pull Request.
