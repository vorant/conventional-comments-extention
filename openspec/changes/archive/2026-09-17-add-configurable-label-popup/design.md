## Context

Текущий MVP состоит из `manifest.json`, одного content script и CSS. `src/content-script.js` содержит константу `LABELS`, строит панель над GitHub textarea и вставляет выбранный префикс. Manifest пока не объявляет `action`, popup или permissions, а тесты на `node --test` проверяют минимальный manifest и поведение content script через fake DOM.

## Goals / Non-Goals

**Goals:**

- Добавить popup-настройки без сборщика и внешних зависимостей.
- Хранить пользовательский список labels между сессиями браузера.
- Использовать один и тот же дефолтный список в popup и content script.
- Сохранить GitHub-only scope content script.
- Оставить панель labels компактной и встроенной в существующий GitHub review UI.

**Non-Goals:**

- Синхронизация настроек с сервером проекта или backend.
- Поддержка GitLab, Bitbucket, decorations `(non-blocking)` или AI-подсказок.
- Drag-and-drop сортировка, импорт/экспорт настроек и отдельная options page.

## Decisions

### Хранить labels в `chrome.storage.sync`

Использовать ключ `ccLabels` со значением массива строк. `storage.sync` лучше подходит для пользовательских настроек Chrome-расширения, чем `storage.local`, потому что сохраняет небольшие предпочтения пользователя между браузерными профилями при включенной синхронизации. Если API недоступен в тестовом окружении, код должен иметь небольшой adapter/fallback, возвращающий дефолтные labels.

Альтернатива: `storage.local`. Она проще и имеет меньше ограничений квот, но для короткого списка labels квоты `sync` не должны быть проблемой, а ожидаемое поведение настроек расширения ближе к синхронизируемым preferences.

### Держать дефолтный список в обоих runtime contexts

Content script и popup работают в разных контекстах MV3, без сборщика и shared module. Чтобы не вводить build step, дефолтный список можно продублировать в `src/content-script.js` и `src/popup.js`, а static test должен проверять совпадение этих списков.

Альтернатива: добавить shared JS-файл. В content script это потребует подключения дополнительного файла в manifest или перехода на module-like схему, что усложняет текущий минимальный MVP.

### Popup сохраняет список автоматически после действий пользователя

Popup должен отображать строки labels как редактируемые inputs с кнопкой удаления для каждой строки и отдельным control для добавления нового label. Изменение текста, добавление и удаление сохраняют весь массив. Пустые или whitespace-only новые labels не добавляются; отредактированные пустые строки не должны приводить к кнопкам с пустым названием в панели.

Альтернатива: отдельная кнопка Save. Она дает явный commit, но для маленького popup добавляет лишний шаг и риск потерять изменения при закрытии popup.

### Content script строит panel после асинхронной загрузки labels

При обнаружении textarea content script должен загрузить сохраненный список, отфильтровать пустые значения и построить panel только если список непустой. Если список пустой, textarea все равно можно пометить обработанной, чтобы MutationObserver не пытался постоянно добавить пустую panel к тому же полю.

Альтернатива: всегда показывать panel и текст вроде "Нет labels". Это добавило бы интерфейс вне прямого действия пользователя в GitHub UI и противоречит требованию не показывать пустую панель.

### Обновление уже открытых panels

Если пользователь меняет labels в popup, новые GitHub comment fields должны использовать сохраненный список. Для уже открытых panels можно подписаться на `chrome.storage.onChanged` и перерисовать существующие panels, но это не обязательно для базового сценария popup -> GitHub. Реализация может включить подписку, если она останется простой и тестируемой.

Альтернатива: требовать refresh страницы Pull Request. Это проще, но выглядит как шероховатость для настройки, которая должна применяться естественно.

## Risks / Trade-offs

- `storage.sync` асинхронен, а content script сейчас полностью синхронный -> тесты должны покрыть создание panel после async загрузки.
- Popup добавляет permission `storage`, поэтому static test и README должны явно отражать новое разрешение.
- Дублирование дефолтного списка в двух файлах может разъехаться -> добавить static test на совпадение списков.
- GitHub DOM остается динамическим -> сохранить текущую логику `MutationObserver`, `data-cc-label-panel` и insertion target для нового GitHub UI.

## Migration Plan

1. Добавить popup и `storage` permission в manifest.
2. При первом открытии popup или первом запуске content script использовать дефолтный список, если `ccLabels` еще не сохранен.
3. Не выполнять миграцию данных для существующих пользователей версии `0.1.0`, потому что пользовательских настроек в ней нет.
4. Rollback: удалить popup/action/storage usage и вернуть статический список labels в content script.
