## Context

Мотивация описана в proposal.md. Сейчас `content-style.css` подключается через manifest и worker и содержит одновременно оформление панели и диагностики. Профили хранятся в `chrome.storage.local`; worker сериализует изменения. Форма хранит черновик и версии операций для каждого профиля, но валидирует весь профиль целиком. Изменение затрагивает хранение, форму и жизненный цикл content script, поэтому требует общего дизайна.

## Goals / Non-Goals

**Goals:** единый источник стандартного CSS, независимый сброс CSS без потери других черновиков, сохранение действующей модели профилей и очереди записи.

**Non-Goals:** визуальный конструктор, подсветка синтаксиса с новой зависимостью, редактор оформления всего сайта, popup или диагностики; дополнительные профили и синхронизация CSS между устройствами.

## Decisions

1. **Полный CSS вместо добавочного слоя.** Вынести текущие правила `.cc-label-panel` и `.cc-label-button`, включая состояния, в общий ресурс стандартов, доступный форме и content script. `content-style.css` оставить для диагностики. Один динамический style-элемент содержит эффективный CSS активного профиля. Это позволяет удалять правила в редакторе без скрытого стандартного слоя. Альтернатива с дополнительными overrides проще, но удаление показанного правила тогда не соответствовало бы результату.

2. **Необязательное поле `panelCss` в overrides профиля.** Отсутствие означает актуальный стандарт; строка, включая пустую, означает пользовательский текст. Хранить исходное форматирование. Не дублировать стандарт в каждом сохранении других полей. Старые настройки остаются совместимыми со схемой 1. Некорректный тип поля при чтении заменяется стандартом независимо от остальных настроек. Полный сброс удаляет все overrides профиля, отдельный сброс удаляет только `panelCss`.

3. **Обычная textarea и отдельная операция записи CSS.** Стандартный текст показывается реальным значением поля с отключённой проверкой орфографии и моноширинным шрифтом. Существующую очередь worker расширить операциями изменения и сброса CSS по id профиля; они объединяются с последним сохранённым состоянием. Сохранение остальных полей не должно возвращать устаревший CSS. Черновики и версии CSS учитывать отдельно, чтобы ошибка адреса не блокировала восстановление стилей. Показывать состояние записи CSS рядом с блоком. Полный сброс профиля согласует обе группы черновиков и ожидающих операций.

4. **Нативная обработка CSS.** Не вводить собственный парсер и не отвергать промежуточный текст при вводе. CSS передаётся как текст, без HTML-интерполяции. В подсказке указать назначение классов панели и кнопок и то, что браузер игнорирует неподдерживаемые правила. Это обычный CSS в документе сайта: автоматическое ограничение произвольных пользовательских селекторов и sandbox CSS не обещаются. Стандартные правила используют только классы расширения. Внешние импорты, ресурсы и ограничения CSP не требуют новых разрешений и не обходятся расширением.

5. **Обновление на месте.** Подключать общий ресурс до потребителей в options, manifest и динамической регистрации. Обновлять или удалять единственный собственный style-элемент при изменении эффективного CSS и выборе профиля. Не трогать значение редактора и не дублировать панели. Учесть текущий observer, чтобы изменение style-элемента не вызывало бесконечную обработку.

## Risks / Trade-offs

- Пользовательский CSS может скрыть панель или затронуть страницу → доступная отдельно страница настроек и сброс CSS позволяют восстановить оформление; подсказка направляет к классам панели.
- Нативный CSS-парсер молча игнорирует ошибки → сохранять исходный текст и явно описать это поведение, не обещать строгую валидацию.
- Полная копия пользовательского CSS не получает будущие изменения стандартов → обновления получают профили без переопределений; «Восстановить» возвращает актуальные стандарты.
- Гонки полного и частичного сохранения → операции слияния в worker и тесты задержанных ответов, переключения профиля и сброса во время записи.
- DOM-стенд не рассчитывает CSS → дополнить тесты визуальной проверкой в Chrome; результат реальных GitLab/Bitbucket проверяется отдельно по принятой в проекте практике.

## Migration Plan

Добавить необязательное поле без массовой перезаписи данных. В одном обновлении переключить все пути подключения на общий ресурс стандартов и динамический CSS панели; сохранить диагностику. Проверить старые настройки, новые и уже открытые вкладки. При откате к прежней версии неизвестное поле не применяется; штатное статическое оформление восстанавливается после перезагрузки расширения и вкладок.
