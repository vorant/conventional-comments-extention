## Context

Мотивация описана в proposal.md. Интерфейс версии 0.2.0 уже английский; текущий README русский, содержит команды разработки, схемы хранения и миграции. test/static.test.js явно проверяет русский README. Makefile упаковывает manifest.json, src и README.md, поэтому добавление относительных ссылок требует согласования состава документации в ZIP. Готовых публикационных изображений в docs нет.

Design нужен для решений о сохранности исходного текста, достоверности скриншотов и упаковке ссылочных файлов; delta specs пропускаются как для документационного изменения.

## Goals / Non-Goals

**Goals:** отделить краткую английскую пользовательскую инструкцию от полного технического материала; получить настоящие снимки текущего UI и независимый от Markdown текст магазина; обеспечить читаемые ссылки в репозитории и распакованном архиве.

**Non-Goals:** изменение runtime, локализации, разрешений, схем данных, гарантий совместимости; публикация или настройка аккаунта магазина; разработка рекламных баннеров, privacy policy или полного пакета публикации; перевод всей исторической технической документации.

## Decisions

### Сохранить исходный README полностью

README-DEVELOPER.md получает точную копию исходного README на момент начала apply, включая русскоязычный текст. Сверить с исходным Git blob до дополнений. Затем разрешена отдельная вводная заметка на английском со ссылкой на новый README и актуальный протокол english-interface: русские подписи/каталог в перенесённом тексте описывают прежнее состояние. Существующие разделы не удалять и не сокращать. Это сохраняет явно запрошенное «всё описание»; полный перевод/редактура технического материала отложены.

### Краткий английский пользовательский текст

README: назначение и атрибуция; How to use (открыть inline editor, выбрать label, дописать и отправить штатной кнопкой сайта); Customize labels (текст, порядок, цвет, необязательные emoji); Company repositories; ссылка Developer documentation. Ориентир 350–550 слов без alt-текста и подписей. Примеры комментариев — собственные, короткие, на английском. Не копировать маркетинговые утверждения оригинального проекта и не обещать автоматическую отправку, AI, настройку decorations либо официальную аффилиацию.

Источник идеи и формата — [Conventional Comments](https://conventionalcomments.org/), проверен 2026-09-25. Ссылка обязательна и в README, и в тексте магазина. Не придумывать URL ещё не опубликованной страницы расширения.

docs/chrome-web-store-description.txt содержит только готовый английский текст для поля описания: примерно 200–350 слов, назначение, короткие шаги использования и подключения company site, границы GitLab/Bitbucket, атрибуция с полным URL. Изображения загружаются отдельно; Markdown-ссылки на локальные картинки в этот текст не включать. Альтернатива копирования Markdown целиком хуже из-за относительных ссылок и технических разделов.

### Корпоративные репозитории через настройки браузера

Инструкция использует точные подписи: Settings → Profile → Site URL (origin без пути) → Pages (one path per line) → Saved → Allow site access. Пример GitLab: https://git.company.example и /*/-/merge_requests/*. Объяснить, что настройка меняет выбранный встроенный профиль, а не создаёт дополнительный: один адрес на профиль. Editor CSS selector менять только при необходимости для конкретного редактора. GitLab — Markdown mode; GitLab/Bitbucket preview, совместимость редакторов не гарантируется. На стороне репозитория ничего добавлять не требуется. Доступ выдаётся отдельно после сохранения; отказ не означает успешное подключение.

### Реальные снимки текущего UI

Минимум три PNG: docs/screenshots/review-comment.png, labels-popup.png, company-settings.png. Снимать установленное расширение в отдельном Chrome-профиле с английскими данными и обезличенным примером кода. Основной кадр — реальный публичный GitHub PR с открытым inline editor и вставленным префиксом; комментарий не отправлять. Popup — штатная ширина, без растягивания UI; настройки — пример company origin без выдачи доступа реальному корпоративному хосту и без ложного статуса подключения.

Если живой GitHub недоступен, использовать настоящий content script на локальном демонстрационном review-fixture; явно подписать кадр как demo в README и протоколе, не представлять стенд проверенным GitHub/GitLab. Не использовать нарисованный или AI-сгенерированный интерфейс. Не показывать приватный код, аккаунты или внутренние адреса.

README может использовать кадры естественных размеров. Дополнительно сохранить не менее одного пригодного для магазина снимка реального UI в docs/screenshots/store/ с размером 1280×800 либо 640×400, без декоративных полей. Это соответствует [официальным требованиям к screenshots](https://developer.chrome.com/docs/webstore/images#screenshots), проверенным 2026-09-25; перепроверить перед экспортом. Не масштабировать узкий popup до ширины кадра: снимать его в реальном контексте браузера, либо использовать review/settings для store asset. Подписи и alt на английском. Снимки визуально проверить в исходном и уменьшенном размерах.

В docs/documentation-verification.md записать среду, источник каждого кадра (live/demo), воспроизведение, размеры, проверку ссылок и ограничения. Это технический протокол, не часть описания магазина.

### Согласовать проверки и ZIP

Заменить существующую проверку русского README проверкой новой роли файлов: английские пользовательские разделы, атрибуция, ссылка на developer README и существующие PNG. Не вводить новый фреймворк тестов и не фиксировать весь текст строковыми snapshot.

Makefile включает README-DEVELOPER.md и docs вместе с README.md: это сохраняет изображения и цепочки относительных ссылок из перенесённого текста. src уже включает vendor README/лицензии. Тесты, OpenSpec и скрытые файлы по-прежнему исключены. Альтернатива абсолютных ссылок не подходит для локального просмотра ZIP и требует стабильного опубликованного URL. Проверить относительные ссылки всех включённых Markdown-файлов после распаковки; ссылки на разработческие исходники при необходимости явно обозначить как относящиеся к checkout, а не установочному ZIP.

## Risks / Trade-offs

- Исходный русский текст содержит устаревшие UI-названия → сохранить полностью, отделить вводной заметкой от актуальной английской инструкции.
- Живой GitHub или вход недоступны → честно обозначенный demo с настоящим расширением; не выдавать его за проверку сайта.
- Текст может создать ожидание поддержки любой корпоративной системы → назвать конкретные профили и ограничения редактора.
- Документация увеличивает ZIP → включать небольшой набор оптимизированных PNG, проверить итоговый размер и читаемость.
- Материалы могут восприниматься как завершённая публикация → итог явно описывает готовность текста/скриншотов, не статус магазина.

## Migration Plan

Сначала сохранить исходный README, затем написать пользовательские документы, снять интерфейс и проверить Markdown/ZIP. Сравнение исходного текста, npm test и строгая валидация OpenSpec завершают приёмку. Изменения хранилищ не нужны. Откат — возврат документационных файлов, теста и Makefile через Git; пользовательские данные не затрагиваются.
