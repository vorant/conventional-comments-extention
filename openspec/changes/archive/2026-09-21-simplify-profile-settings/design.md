## Context

Мотивация описана в `proposal.md`. Сейчас `site-profiles.js` объединяет произвольные overrides и custom, `profile-settings.js` сохраняет форму по submit и блокирует действия флагом busy. Worker уже последовательно обрабатывает записи через очередь, затем обновляет регистрации и вкладки. `panel-engine.js` использует контейнер и специальную обёртку GitHub; Bitbucket использует rich-text адаптер. Простое скрытие полей оставило бы старые overrides и пользовательские профили действующими.

Дизайн необходим из-за изменения общей модели профилей и асинхронного сохранения в popup и worker.

## Goals / Non-Goals

**Goals:** единая нормализация профилей во всех контекстах, сохранение последнего корректного ввода без гонок, совместимость существующего хранилища.

**Non-Goals:** новые типы редакторов, улучшение селекторов GitLab/Bitbucket без проверки живого DOM, изменение labels и темы, новые зависимости. Не удаляем внутренние функции анализа DOM, используемые автоматическим размещением, только потому что удалена кнопка проверки.

## Decisions

### Нормализовать эффективные профили на общей границе

В `site-profiles.js` строить ровно три профиля из defaults и разрешённых overrides: origin, paths, editorSelector, placement (`before`/`after`). name, enabled, editorAdapter, containerSelector, anchorMode и anchorSelector брать из defaults; enabled всегда true. Сохранение неизвестного id отклонять, сброс разрешать только встроенным id. Применять эти ограничения и в worker, чтобы скрытие UI не было единственной защитой модели.

Сохранить schemaVersion 1 и старые custom в хранилище, но исключить их из эффективных профилей и выбора. Чтение не переписывает хранилище. Допустимые старые поля сохраняются; недопустимые отдельные поля и prepend/append получают default. Неизвестный формат по-прежнему не перезаписывается. Это позволяет обойтись без разрушительной миграции. Альтернатива — новая схема с удалением старых данных — не нужна для упрощения UI.

При пересечении встроенных профилей оставить существующее поведение первого совпадения в порядке defaults (GitHub, GitLab, Bitbucket); удаляется только приоритет custom. Сохранение не вводит новые ограничения на пересечения.

### Сохранить предустановленное размещение

Единственное поле селектора относится к редактору. Селектор может содержать несколько альтернатив через запятую. Контейнер и обёртка остаются внутренними деталями профиля: GitHub сохраняет wrapper, Bitbucket — rich-text адаптер. UI положения содержит только before/after. Альтернатива — удалить контейнеры и всегда вставлять рядом с найденным DOM-узлом — может сломать расположение GitHub и визуальные редакторы.

### Автосохранение по input/change с упорядоченными снимками

После каждого события валидировать весь текущий черновик и сразу передавать корректный снимок с id профиля в очередь worker; не использовать debounce, зависящий от жизни popup. Не дублировать одинаковые снимки при input и change. Невалидный черновик остаётся в форме, но не отправляется. Показывать «Сохранение…», «Сохранено» или ошибку; для ошибки записи предоставить повтор через изменение поля или отдельное действие повтора, не возвращая постоянную кнопку «Сохранить».

Заменить глобальный busy для редактирования учётом последовательности запросов и черновиков по id. Ответ обновляет статус только соответствующей версии формы; не перерисовывать всю форму после каждого ответа. Переключение профиля не отменяет отправленные записи и не переносит значения между профилями. Worker сохраняет порядок сообщений и не отбрасывает новые изменения во время записи. Не сообщать об успехе до подтверждения операции.

Сброс отправляется после ранее принятых записей выбранного профиля; сбрасывает локальный черновик и делает старые ответы неактуальными. Новые изменения после сброса идут после него. Альтернатива с существующим busy теряет ввод, а повторный load после каждой записи сбивает курсор и может вернуть устаревшие значения.

### Разделить сохранение и доступ

Оставить явную кнопку запроса разрешения. Запрашивать доступ синхронно из клика для валидного адреса показанного профиля; кнопку отключать, пока этот снимок не подтверждён сохранением. После предоставления доступа запускать существующий refresh. Обновить тексты, чтобы они не предлагали нажать «Сохранить» или «Проверить профиль». Автосохранение не вызывает запрос разрешения.

### Сохранить автоматическую диагностику

Удалить UI и обработчик явной проверки в настройках. Удалить исключительно связанные с ней ветви сообщений cc-check/cc-inspect, если они не используются другими сценариями, сохранив inspect движка размещения и переход из уведомления к профилю. Переписать подсказки `panel-engine.js`, `editor-adapters.js` и popup: без ссылок на удалённые настройки. Альтернатива — удалить диагностику целиком — лишает пользователя объяснения отсутствующей панели.

## Risks / Trade-offs

- Скрытые параметры больше нельзя исправить для нестандартной корпоративной версии → явно описать ограничение предустановленных адаптеров в документации; не заявлять новую совместимость.
- Частые сохранения вызывают обновление вкладок → не отправлять одинаковые снимки, сохранить последовательность worker; проверить фокус, текст и отсутствие дублирующихся панелей.
- Закрытие popup уничтожает обработчики ответов → корректные изменения отправлять сразу, запись выполняет worker; статус «Сохранено» показывать только после подтверждения.
- Сохранённый CSS может быть синтаксически верным, но не находить редактор → автосохранение проверяет синтаксис, а не наличие DOM на активной странице; автоматическая диагностика сохраняет прежние границы.
- Старые custom перестают работать → объяснить переход в README; оставленные данные позволяют откат версии без удаления исходной конфигурации.

## Migration Plan

1. Внедрить общую нормализацию и ограничения записи, затем упрощённый UI и автосохранение.
2. При запуске/обновлении существующий reconcile пересчитает регистрации только по встроенным профилям и очистит устаревшие панели в доступных вкладках. Разрешения браузера автоматически не отзывать.
3. Проверить старое хранилище с custom, disabled, нестандартными скрытыми полями и placement; проверить повторный запуск и сброс без изменения labels/темы.
4. Обновить документацию, выполнить тесты и ручную проверку popup. После реализации синхронизировать delta specs и архивировать change.
5. Откат: вернуть предыдущую версию расширения; custom остаются в хранилище. Overrides профилей, которые пользователь успел изменить или восстановить, автоматически к прежним значениям не возвращаются.
