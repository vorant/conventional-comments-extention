## Context

Мотивация описана в proposal.md. Сейчас один content script проверяет hostname GitHub, ищет textarea, выбирает GitHub-wrapper и вставляет панель. MutationObserver поддерживает динамические формы. Labels и тема уже сохраняются через chrome.storage.sync; popup управляет ими. Тесты используют node:test и собственный DOM-стенд. CSS панели использует переменные GitHub с fallback-цветами.

Изменение затрагивает модель настроек, жизненный цикл content script и UI, поэтому требует отдельного дизайна. Реальный DOM GitLab и Bitbucket в этой сессии не проверялся; корпоративных стендов у пользователя нет. По последующему явному решению пользователя реальная проверка GitLab/Bitbucket передана ему; текущая реализация поставляет предварительные профили и проверяет синтетические fixtures локально. Они не подтверждают реальную совместимость.

## Goals / Non-Goals

**Goals:** отделить конфигурацию DOM от общего поведения labels, поддержать несколько редакторов одновременно, дать пользователю управляемую диагностику и возможность восстановления профиля.

**Non-Goals:** выполнение пользовательского JavaScript, универсальная поддержка любого rich-text редактора, обход закрытого Shadow DOM и cross-origin iframe, автоматическое угадывание селекторов, отправка комментариев расширением.

## Decisions

### 1. Декларативные профили и проверенные адаптеры

Профиль содержит id, имя, enabled, templateId, точный origin, маски pathname, editorSelector, containerSelector, необязательный anchorSelector, placement и editorAdapter. Маски пути используют только литералы и `*`; query и hash не участвуют. Контейнер находится через ближайшего предка редактора; anchor ищется внутри этого контейнера. Пустой anchor означает сам редактор. Позиции: before, after, prepend, append; последние две допустимы для контейнеров, но не для textarea или void-элементов. UI предлагает простые варианты «над»/«под» и расширенные поля.

Общее ядро отвечает за labels, наблюдение DOM, панель и диагностику; адаптер отвечает за чтение, вставку, фокус и уведомление редактора об изменении. Базовый адаптер поддерживает textarea. GitLab-профиль использует textarea в Markdown-режиме, Bitbucket — экспериментальную штатную операцию браузера insertText для визуального редактора. Проверка поведения на реальных сайтах передана пользователю. Произвольный contenteditable не считается автоматически поддержанным. Пользователь выбирает из поставляемых адаптеров, а не вводит код.

Альтернатива — единый набор широких селекторов и присваивание value всем полям — не решает различия редакторов и создаёт ложное ощущение совместимости.

### 2. Настройки в существующем popup

Добавить раздел «Сайты» с формой выбранного профиля, созданием из шаблона или вручную, сохранением, отключением, удалением пользовательского профиля и сбросом переопределений. Labels остаются общими. Настройки профилей хранить отдельно в chrome.storage.local со schemaVersion: корпоративные адреса не требуется синхронизировать вместе с labels. Валидация адреса, маски и селекторов предшествует сохранению; ошибка оставляет рабочую конфигурацию неизменной.

Встроенные defaults поставляются как данные, пользовательские overrides хранятся отдельно. При пересечении профилей пользовательский профиль имеет приоритет над встроенным; несколько пользовательских профилей с пересекающимися масками одного origin отклоняются при сохранении с объяснением конфликта. Это обеспечивает единственный профиль страницы без неявного дублирования панелей.

### 3. Подключение сайтов и жизненный цикл

Сохранить существующий доступ GitHub. Для дополнительных HTTP(S) origins использовать optional host permissions и запрашивать конкретный origin по действию пользователя. Service worker регистрирует content scripts на разрешённых origins и сверяет регистрации при старте, изменении профилей и разрешений. Маски страниц дополнительно проверяются внутри скрипта; подключение на origin позволяет обработать SPA-переход на MR/PR. Точные API и минимальную версию Chrome проверить по официальной документации при реализации.

Регистрация должна исключать двойное подключение GitHub; единый bootstrap защищён от повторной инициализации. Для уже открытой вкладки после подключения выполняется контролируемая инициализация. Отказ или отзыв доступа отражается в настройках. Отключение профиля, переход на неподходящий путь и отзыв доступа прекращают обработку и удаляют UI в доступных активных контекстах; недоступная вкладка очищается при следующей загрузке.

Альтернатива — постоянный доступ ко всем сайтам — не требуется для адресного подключения. Одной статической записи manifest недостаточно для произвольных корпоративных адресов.

### 4. Размещение и повторная обработка

Состояние вести для каждого редактора, а не запрещать вторую панель во всём form. Поиск anchor не должен брать элемент соседнего комментария: отсутствие однозначной привязки считается ошибкой. Повторные мутации не создают дубликатов. Если anchor ещё не появился, повторить поиск после стабилизации DOM (начальный интервал 500 мс), затем показать ошибку; дальнейшее появление anchor автоматически восстанавливает панель. При замене DOM-узлов удалённые панели освобождаются. Изменение профиля переобрабатывает активные редакторы без изменения их текста.

Стили панели получают собственные переменные и изолированные классы с fallback, чтобы переменные GitHub не были обязательными.

### 5. Диагностика без ложных тревог

Автоматическая ошибка появляется только при найденном поддерживаемом редакторе и недоступном/неоднозначном месте панели, после повторной проверки. Сообщение вне anchor, в независимом контейнере расширения на странице, содержит имя профиля и «Открыть настройки профиля». Действие открывает extension-страницу настроек нужного профиля (можно использовать тот же popup-документ в отдельной вкладке). Это внутристранничное уведомление, без системного notifications permission.

Одно уведомление на профиль и тип ошибки в пределах документа и ревизии настроек. Закрытие подавляет повторы; успешное восстановление убирает устаревшую ошибку. Пустой список labels не порождает ошибок размещения. Отсутствующий редактор не порождает автоматических уведомлений.

«Проверить профиль» в popup работает с активной вкладкой: отдельно показывает доступ, соответствие URL, наличие редакторов, поддержку их типа и однозначность anchor. При отсутствии редактора предлагает открыть поле и повторить проверку. Проверка не изменяет текст и не отправляет комментарий. Отсутствие связи с вкладкой показывается отдельным результатом, а не как отсутствие редактора.

## Risks / Trade-offs

- Различия Cloud и корпоративных версий → готовый шаблон является отправной точкой; документировать проверенные варианты и позволять overrides, не обещая проверки всех версий.
- Сложные редакторы → маркировать GitLab/Bitbucket предварительными; предоставить пользователю проверку профиля и инструкцию ручной приёмки.
- Неверный широкий селектор → ограничивать поиск контейнером редактора, диагностировать неоднозначность, тестировать несколько открытых комментариев.
- Частые DOM-мутации → объединять сканирования, ограничивать область поиска и подавлять повторы уведомлений.
- Удалённый или изменённый anchor → повторная обработка и очистка UI без потери текста.

## Migration Plan

Добавить версионированные defaults/overrides без изменения ccLabels и темы. Для существующей установки GitHub работает с прежним поведением до переопределения. Новые сайты подключаются после выдачи доступа. Обновить README, DOM-заметки, требования и тесты; после реализации синхронизировать delta specs и архивировать этот change. Для отката отключить новые профили и регистрации, сохранив labels и тему; старый GitHub-профиль должен оставаться рабочим.
